# CustomWorkFlow 的灵魂（Soul）

> 本文档是 CustomWorkFlow 的核心思想（Soul），也是整个 `spec/` 的**全局入口**，
> 说明它「为什么存在」以及「如何做决策」。
> 当具体的 schema、skill 或 CLI 行为与本文冲突时，以本文所述的取向为准去修正它们。

## 0. 如何阅读 spec（前缀约定）

为了让 agent 在 vibecoding 时**不必每次全量读取 spec，只读当前需要的约束**，`spec/` 下每个文档用文件名前缀标注读取必要性：

| 前缀 | 含义 | 何时读 |
| --- | --- | --- |
| `[Must Read]` | 全局必读入口 | **任何**任务开始前都要读（本文） |
| `[分析必读]` | 需求分析阶段的前置约束 | **仅**在 PRD 分析阶段必读 |
| `[架构必读]` | 架构级约束 | 涉及「规划 / 拆解一个 change」时必读 |
| `[模块选读]` | 模块级约束 | 实施某个模块 / 子 change 时按需读 |
| `[任务选读]` | 单任务级约束 | 处理该具体环节（如归档）时才读 |
| `[UI控件必读]` | UI 控件映射库路由入口 | 涉及 UI 控件的拆解（propose）与实施（apply）时必读；读它做分流，再按路由读 `ui-components/` 下对应大类明细 |
| `[经验必读]` | 团队经验沉淀库（跨切面兜底） | propose / apply / archive 时必读；沉淀「反复纠正后的通用规则」中不属于任何单一阶段文档的那部分 |

当前 spec 目录：

- `[Must Read] soul.md` —— 本文，全局思想与入口。
- `[分析必读] preflight.md` —— 任务拆解前的 PRD 分析约束。
- `[架构必读] propose.md` —— 提案与任务拆解阶段的约束（MVVM 拆解、拓扑依赖）。
- `[模块选读] apply.md` —— 实施与协作分派阶段（多 change 拆分、`comate.md` 责任台账）。
- `[任务选读] archive.md` —— 归档阶段的约束。
- `[UI控件必读] ui-components.md` —— UI 控件映射约定库的**路由入口**（通用规则 + 大类路由表；UI 模式 → 指定实现，如 tab → MagicIndicator）。具体实现按大类拆在同目录 `ui-components/` 下（如 `ui-components/tab-导航-banner.md`），命中哪个大类只读哪个。
- `[经验必读] lessons.md` —— 团队经验沉淀库的**兜底文件**：只收「反复纠正 → 蒸馏成的通用规则」中**不属于任何单一阶段文档**的跨切面条目。能归入 preflight/propose/apply 或 UI 控件库的，一律折叠进那里，不进本文件。见其内「使用规则」。

> 读取原则：先读本文确定当前处于哪个阶段，再按前缀只加载对应阶段的文档。

## ★ 通用约束：设计稿一律经 Figma MCP 读取（贯穿所有阶段）

> 本约束**不限阶段、不限时机**——无论在 preflight 分析、propose 拆解还是 apply 实施，只要收到 Figma / 设计稿链接就适用。

- 收到 Figma 链接（`figma.com/file`、`figma.com/design`、`figma.com/proto` 等）时，**必须调用 `figma-use` skill，经 Figma MCP 读取真实结构化设计数据**：图层 / 节点结构、文本内容、尺寸与间距、颜色、组件与变量、约束与自动布局等。
- **严禁仅凭截图、缩略图或链接预览图判断设计内容**——截图丢失结构、尺寸、状态与命名，据此判断必然不准确。
- Figma MCP **未授权 / 不可用 / 链接无法访问时**：先按 skill 指引完成授权（如 OAuth）；仍不可用则**停止并请用户提供可读取的设计数据**，不要退回到截图猜测。
- 读到设计数据后，与 PRD / 需求描述**综合分析**：以 Figma 结构化数据为「界面事实」，PRD 为「意图与规则」，二者对照。
- 各阶段的具体用法：分析阶段见 `[分析必读]preflight.md` 第 1.1 节；拆解与实施阶段把 Figma 结构化数据作为 UI 控件识别（配合 `[UI控件必读]ui-components.md`）与还原的事实来源。

## ★ 通用约束：git 操作不自动执行（贯穿所有阶段）

> 本约束**不限阶段、不限时机**。

- **`pull` / `push` / `commit` / `merge` / `checkout` 等一切 git 操作，不得由 agent 自动执行**——须由人工完成，或在**用户明确确认后**才执行。
- **写文件不受限**：编辑 `spec/`、change 目录下的 `comate.md` / `decisions.md` / 代码等属于正常工作，可直接进行；受限的只是「把改动落入版本库 / 与远端同步」这类 git 动作。
- 需要 git 操作时（如并行窗口要同步、要提交决策），**提示用户「需要执行 X」并等待其确认或让其自行执行**，不要擅自跑 git。
- 工作流文档与 skill 步骤里，**不要写「agent 自动 git pull / commit」**这类指令；涉及同步处一律写成「提示用户 pull / commit」。

## 1. 我们是谁

CustomWorkFlow 是在 [OpenSpec](https://github.com/) SDD（Spec-Driven Development，规格驱动开发）思路上改造而来的**任务拆解和SDD框架**，专门面向 **Android / 移动端** 工程。

它继承 OpenSpec 的核心链路——
**proposal（提案）→ specs（规格）→ design（设计）→ tasks（任务）→ apply（实施）→ archive（归档）**——
但针对移动端研发的两个真实痛点做了重新设计。

## 2. 我们要解决的两个问题

OpenSpec 是一套通用的 SDD 框架，直接用在 Android 项目上会暴露两个缺陷。CustomWorkFlow 存在的全部理由，就是补齐它们：

1. **UI 还原度差**——从 Figma 设计稿到 Android 界面，AI 无法做到像素级对齐。
2. **团队协同弱**——OpenSpec 的一个 change 默认是「一个人 / 一个 agent 从头做到尾」，缺少可拆分、可分派、可追踪责任人的协作模型。

下面两节分别说明我们的立场与解法。

## 3. 核心信条

### 信条一：诚实面对 AI 的能力边界（UI 还原度）

我们**承认**：在 Figma → Android 的还原上，存在约 **20% 的差距是 AI 无法自动对齐的**（间距的视觉手感、字体渲染差异、状态动效、机型适配、设计师的隐性意图等）。

因此我们做出一个明确的价值取舍：

- **AI 只负责搭建 UI 框架**——布局结构、控件层级、可复用组件、主题与基础样式、数据绑定占位。
- **AI 不追求 UI 100% 对齐**——刻意不为最后那 20% 的像素级细节反复消耗算力和时间。
- **那 20% 留给人类**——由工程师 / 设计师在 AI 搭好的框架上做最终校准。

> 这不是能力的妥协，而是分工的清醒：让 AI 做它擅长且高效的 80%，把需要人类审美与判断的 20% 明确交还给人。追求 100% 自动对齐，往往会让整体产出更慢、更不可控。

### 信条二：为团队协作而拆解（团队协同）

CustomWorkFlow 的任务拆解，第一优先级不是「让一个 agent 更好地独立完成」，而是**「让任务能被多个人 / 多个 agent 并行认领与协作」**。

拆解与协同的具体原则见下一节。

## 4. 任务拆解方法论

### 4.1 以架构模式（MVVM / MVI）作为拆解的第一刀

移动端界面适配单向、可观察的状态驱动架构。一个界面级的 change，首先**选定架构模式**，再沿它切成两个可并行的大任务：**View 层** 与 **状态 / 逻辑层**。

- **模式由用户在 propose 时选择**（MVVM 或 MVI），不擅自默认；选定结果写进 `design.md`，apply 按此实现。
  1. **MVVM**：**UI 任务**（View：界面、布局、控件、样式、交互框架）＋ **ViewModel 任务**（状态、数据流、业务逻辑、与数据层交互）。契约 = ViewModel 暴露的可观察数据 / 状态。
  2. **MVI**：**UI 任务**（View：渲染唯一不可变 State、向上发出 Intent）＋ **State/Reducer 任务**（Intent → State 的单向数据流、业务逻辑、与数据层交互）。契约 = State 数据类 + Intent 事件集。

这一刀（无论哪种模式）天然让「视觉还原（信条一）」与「逻辑实现」解耦，两类工作可以由不同专长的人并行推进。

### 4.2 UI 任务再按模块控件拆解

UI 大任务不作为一个整体交付，而是继续拆解为**独立的模块控件**（例如：顶部导航栏、卡片列表项、底部操作栏、空状态、弹窗……）。

- 每个控件是一个可独立开发、可独立认领的子任务。
- 控件应尽量可复用、边界清晰，减少子任务之间的耦合。
- 这样多个人可以同时开发不同控件，最后组装成完整界面。

### 4.3 tasks 之间以拓扑关系梳理依赖

拆出的任务不是一张扁平清单，而是一张**有向依赖图（DAG）**：

- 每个任务显式声明它依赖哪些前置任务（拓扑序）。
- 没有未完成依赖的任务即为「可认领 / 可开始」。
- 依赖关系决定并行度：相互独立的任务可以同时开工，有依赖的任务按拓扑序推进。

> 例：ViewModel 的数据契约 → 各 UI 控件 → 界面组装 → 联调。契约先行，控件并行，组装收敛。

### 4.4 apply 阶段：一个 change 拆解为多个 change

这是 CustomWorkFlow 相对 OpenSpec 最关键的协作扩展。

在规划阶段，一个 change 完成 proposal / specs / design / tasks；进入 **apply（实施）阶段**时，我们不再让单个执行者吞下整个 change，而是**把这一个 change 按上面的拆解结果，拆成多个可独立实施的子 change**：

- 每个子 change 对应一块可交付的工作（一个 ViewModel、一组控件、一次组装等）。
- 子 change 之间同样遵守 4.3 的拓扑依赖关系。
- 每个子 change 可以分派给不同的人 / agent 并行 apply。

### 4.5 用 comate.md 记录责任人

每个（子）change 目录下维护一份 **`comate.md`**，作为该 change 的**协作与责任台账**：

- 记录当前 change 的**负责人（owner）**。
- 记录它依赖 / 被依赖的其他 change（对应拓扑关系）。
- 记录当前状态与交接信息，便于团队随时看清「谁在做什么、卡在哪、下一步谁接」。

`comate.md` 让「团队协同」从口头约定变成可追踪的文件事实，是 CustomWorkFlow 协作模型的落地载体。

## 5. 一句话总结

> **CustomWorkFlow = SDD 的严谨 + 对 AI 边界的诚实（UI 交给人做最后 20%）+ 为团队而生的拆解（架构模式（MVVM / MVI）分层、控件粒度、拓扑依赖、多 change 分派与 comate.md 责任台账）。**
