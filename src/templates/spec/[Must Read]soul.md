## 1. 我们是谁

FallaMercury 是在 [OpenSpec](https://github.com/) SDD（Spec-Driven Development，规格驱动开发）思路上改造而来的**任务拆解和SDD框架**，专门面向 **Android / 移动端** 工程。

它继承 OpenSpec 的核心链路——
**proposal（提案）→ specs（规格）→ design（设计）→ tasks（任务）→ apply（实施）→ archive（归档）**——
但针对移动端研发的两个真实痛点做了重新设计。

## 2. 我们要解决的两个问题

OpenSpec 是一套通用的 SDD 框架，直接用在 Android 项目上会暴露两个缺陷。FallaMercury 存在的全部理由，就是补齐它们：

1. **UI 还原度差**——从 Figma 设计稿到 Android 界面，AI 无法做到像素级对齐。
2. **团队协同弱**——OpenSpec 的一个 change 默认是「一个人 / 一个 agent 从头做到尾」，缺少可拆分、可分派、可追踪责任人的协作模型。

下面两节分别说明我们的立场与解法。

## 3. 核心信条

### 信条一：诚实面对 AI 的能力边界（UI 还原度）

我们**承认**：在 Figma → Android 的还原上，存在约 **20% 的差距是 AI 无法自动对齐的**（间距的视觉手感、字体渲染差异、状态动效、机型适配、设计师的隐性意图等）。

因此我们做出一个明确的价值取舍：

- **AI 只负责搭建 UI 框架**——布局结构、控件层级、可复用组件、主题与基础样式、数据绑定占位。
- **AI 不追求 UI 100% 对齐**——刻意不为最后那 20% 的像素级细节反复消耗算力和时间。
- **那 20% 留给人类**——由工程师 / 设计师在 AI 搭好的框架上做最终校准。

> 这不是能力的妥协，而是分工的清醒：让 AI 做它擅长且高效的 80%，把需要人类审美与判断的 20% 明确交还给人。追求 100% 自动对齐，往往会让整体产出更慢、更不可控。

### 信条二：为团队协作而拆解（团队协同）

FallaMercury 的任务拆解，第一优先级不是「让一个 agent 更好地独立完成」，而是**「让任务能被多个人 / 多个 agent 并行认领与协作」**。

拆解与协同的具体原则见下一节。

## 4. 任务拆解方法论

### 4.1 以 MVVM 作为拆解的第一刀

移动端界面天然适配 MVVM 架构，因此我们把它作为拆解的基本骨架。一个界面级的 change，首先沿 MVVM 切成两个大任务：

1. **UI 任务**——View 层：界面、布局、控件、样式、交互框架。
2. **ViewModel 任务**——状态、数据流、业务逻辑、与数据层的交互。

这一刀天然让「视觉还原（信条一）」与「逻辑实现」解耦，两类工作可以由不同专长的人并行推进。

### 4.2 UI 任务再按模块控件拆解

UI 大任务不作为一个整体交付，而是继续拆解为**独立的模块控件**（例如：顶部导航栏、卡片列表项、底部操作栏、空状态、弹窗……）。

- 每个控件是一个可独立开发、可独立认领的子任务。
- 控件应尽量可复用、边界清晰，减少子任务之间的耦合。
- 这样多个人可以同时开发不同控件，最后组装成完整界面。

### 4.3 tasks 之间以拓扑关系梳理依赖

拆出的任务不是一张扁平清单，而是一张**有向依赖图（DAG）**：

- 每个任务显式声明它依赖哪些前置任务（拓扑序）。
- 没有未完成依赖的任务即为「可认领 / 可开始」。
- 依赖关系决定并行度：相互独立的任务可以同时开工，有依赖的任务按拓扑序推进。

> 例：ViewModel 的数据契约 → 各 UI 控件 → 界面组装 → 联调。契约先行，控件并行，组装收敛。

### 4.4 apply 阶段：一个 change 拆解为多个 change

这是 FallaMercury 相对 OpenSpec 最关键的协作扩展。

在规划阶段，一个 change 完成 proposal / specs / design / tasks；进入 **apply（实施）阶段**时，我们不再让单个执行者吞下整个 change，而是**把这一个 change 按上面的拆解结果，拆成多个可独立实施的子 change**：

- 每个子 change 对应一块可交付的工作（一个 ViewModel、一组控件、一次组装等）。
- 子 change 之间同样遵守 4.3 的拓扑依赖关系。
- 每个子 change 可以分派给不同的人 / agent 并行 apply。

### 4.5 用 comate.md 记录责任人

每个（子）change 目录下维护一份 **`comate.md`**，作为该 change 的**协作与责任台账**：

- 记录当前 change 的**负责人（owner）**。
- 记录它依赖 / 被依赖的其他 change（对应拓扑关系）。
- 记录当前状态与交接信息，便于团队随时看清「谁在做什么、卡在哪、下一步谁接」。

`comate.md` 让「团队协同」从口头约定变成可追踪的文件事实，是 FallaMercury 协作模型的落地载体。

## 5. 一句话总结

> **FallaMercury = SDD 的严谨 + 对 AI 边界的诚实（UI 交给人做最后 20%）+ 为团队而生的拆解（MVVM 分层、控件粒度、拓扑依赖、多 change 分派与 comate.md 责任台账）。**
