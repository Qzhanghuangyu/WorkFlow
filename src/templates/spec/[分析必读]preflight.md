# [分析必读] Preflight（需求分析）阶段约束

Preflight 位于 propose 之前，职责限定为：创建 change、确认 PRD 所述功能是否已实现，并将 PRD 未明确事项记录到 change 目录的 `preflight.md`。

## 1. 强制流程

1. 完整读取 PRD，获得 change 名称和需求范围。
2. 在 preflight 阶段执行 `cwf new change`；后续 propose 不得创建 change。
3. 只读取与当前需求直接相关的代码和文档。不得为了“全面了解项目”无边界扫描整个仓库。
4. 用具体文件、符号、接口或测试支撑实现状态结论。
5. 在 change 根目录创建 `preflight.md`，记录实现状态和 PRD 未明确事项。

## 2. 核心检查范围

### 2.1 状态与交互检查

识别 PRD 中所有带状态的对象、页面和交互，包括但不限于：

- 初始状态；
- 权限允许、拒绝和未授权状态；
- 网络正常、弱网和断网状态；

对于每个状态交互，必须确认：

- 状态由什么条件触发；
- 状态之间如何迁移；
- 状态由前端、服务端还是本地数据决定；
- 状态是否需要持久化；

不得仅根据静态 UI 推断完整交互逻辑。

### 2.2 边界与异常检查

识别 PRD 未明确的边界条件，包括但不限于：

- 最大值、最小值和长度限制；
- 历史版本兼容；
- 灰度、降级和兜底逻辑。

不得用“按现有逻辑处理”“默认兜底”等模糊描述代替明确规则。

### 2.3 代码兼容性检查

识别 PRD 与现有实现无法直接对应的内容，包括但不限于：

- PRD 概念与现有代码、数据模型或接口字段无法映射；
- 所需能力缺少对应 API、权限、错误码或持久化支持；
- PRD 与现有架构约束、历史行为或兼容承诺冲突；
- 实现需要跨模块改造、数据迁移或新增依赖。

必须引用具体代码、接口、模型或约束作为证据。不得仅凭未搜索到结果就断言能力不存在。

## 3. 记录维度与问题类型

每个问题必须分别标注“检查维度”和“问题类型”。二者是独立字段，不得相互替代。

### 3.1 检查维度

每个问题至少归入以下一个维度：

| 检查维度 | 含义 |
| --- | --- |
| Stateful Interactions | 状态、事件、迁移、守卫条件或状态展示未明确 |
| Boundary and Exception Cases | 边界、异常、重试、降级或兜底规则未明确 |
| Code Compatibility Gaps | PRD 与代码、模型、接口、权限或架构无法直接对应 |

### 3.2 问题类型

每个问题必须选择一个主要类型：

| 问题类型 | 含义 |
| --- | --- |
| Missing Definition | PRD 缺少完成设计、开发或验收所需的明确规则 |
| Conflict | PRD、代码、接口、设计或既有约束之间存在冲突 |
| Implementation Risk | 可以实现，但存在明显成本、风险或技术限制 |
| Decision Required | 必须由产品、设计、后端或其他角色作出决定 |

不得只写“有风险”“需要确认”，必须说明具体缺口。

## 4. 问题描述格式

每个问题必须包含：

```markdown
## [检查维度][问题类型] 问题标题

- 检查维度：
- 问题类型：
- PRD 位置：
- 当前理解：
- 不明确或冲突点：
- 可能影响：
- 建议确认项：
- 可选方案：
- 阻塞级别：Blocker / Major / Minor
```

其中：

- 当前理解：必须基于已读取材料；
- 不明确或冲突点：必须描述事实，不做情绪化评价；
- 可能影响：应说明对设计、开发、测试或发布的具体影响；
- 可选方案：可以提出建议，但不得代替产品决策。

## 5. 边界

- 不在 preflight 阶段创建 proposal、specs、design 或 tasks。
- 不在 preflight 阶段修改业务代码或设计实现方案。
- 不要求所有未明确事项在进入 propose 前解决；它们由 `preflight.md` 传递给 propose。
- 即使没有未明确事项，也必须创建 `preflight.md`。
